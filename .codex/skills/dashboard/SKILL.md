# Dashboard Skill

## Purpose
Generate and maintain the SOXL dashboard surfaces:

- Legacy static `dashboard.html`, generated by `scripts/build_backtest_dashboard.py`.
- Current `web/dashboard-v2`, a lightweight-charts UI backed by JSON under
  `dashboard_data/v2/` and optional reruns from `scripts/dashboard_server.py`.

For new frontend work, prefer `web/dashboard-v2` unless the task explicitly
targets the legacy static HTML.

## Dashboard v2 Frontend Rules

Use these rules before editing TradingView-like interactions:

1. Keep chart behavior inside `web/dashboard-v2/src/chart.ts`; keep data
   slicing/comparison logic in `domain.ts`; keep DOM rendering in `render.ts`.
2. Use `lightweight-charts` native interactions for mouse wheel zoom, drag pan,
   touch drag, pinch zoom, axis drag, kinetic scroll, crosshair move, and click.
   Do not reimplement these with date-input rerenders.
3. Keep hover/crosshair updates cheap. Coalesce high-frequency hover changes
   with `requestAnimationFrame`, and update inspector/feature panels without
   rebuilding charts.
4. Main Chart must always show SOXL candles, an SOXL close line, BUY/SELL
   markers, and a visible position overlay. Missing OHLC enrichment must not
   suppress the price line.
5. Chart command buttons and keyboard shortcuts should operate on existing chart
   handles: zoom in/out, pan left/right, reset, and follow latest.
6. Start/End inputs set the visible chart window. The Run button calls
   `/api/run-backtest`, falling back to `127.0.0.1:8765` or a configured
   `?apiBase=` server when static hosting returns `501`, `405`, or `404`.
7. Model JSON must expose model-specific `feature_columns`,
   `snapshot_columns`, row/event `feature_snapshot`, and retention-gate fields
   when the retention audit exists. The UI should show buy/sell feature
   comparisons and clearly label evidence-only models.
8. Verify frontend changes with:
   ```bash
   cd web/dashboard-v2
   npm test -- --run
   npm run build
   ```
   For visual changes, also open the Vite page in Chrome/Browser and capture a
   screenshot that shows nonblank candles, position, NAV, inspector, feature
   comparison, and Data Sources.

### Post-Train Default View
After a training run, the harness should:
1. export `runtime/execution/card/<profile>/<profile>_soxl_daily.csv`
2. rebuild `dashboard.html`
3. default the dashboard to the latest generated version, not the historical best-Sharpe version

For static/Vercel exports, `paper_trading` is the production first-load view
when present. Keep source priority as:
`paper_trading > generated/static dashboard versions`.

Do not export model-card `post_train_review`/PostTrainPreview daily CSVs into
the dashboard. Use retained dashboard exports, model replay freshness, or an
interactive rerun from `scripts/dashboard_server.py` instead.

Production/Vercel status is split across:

- `dashboard_data/production_status.json`: Vercel auth/project/deploy status
  and static export freshness.
- `dashboard_data/production_goal_gates.json`: parsed `Production Goal Gates`
  from `production/check_scheduler_health.sh`.

Paper-trading dashboard rows are enriched from non-dry per-date summary
artifacts under `runtime/soxl/paper_trading/<date>/`. For same-date reruns,
`duplicate_skip/<profile>/summary.json` should outrank the top-level executed
summary so the dashboard shows the currently selected runtime profile even when
idempotency blocks another order. Do not attach dry-run summaries to ordinary
paper rows.

Scheduled Vercel runs should export goal gates after dashboard build and before
`scripts/deploy_vercel_dashboard.py --deploy`, so the deployed static bundle
shows the same blockers as health. Verify with:

```bash
qlib_venv/bin/python scripts/export_production_goal_gates.py
qlib_venv/bin/python scripts/check_dashboard_static_export.py
# expect production_status=<status> goal_gates=<status> paper_latest_signal=<YYYY-MM-DD>
```

### Refresh Model Replays For Static/Vercel

Before scheduled/static dashboard rebuilds, refresh retained model replay CSVs:

```bash
PYTHONPATH=. qlib_venv/bin/python scripts/refresh_dashboard_model_replays.py --python qlib_venv/bin/python
PYTHONPATH=. qlib_venv/bin/python scripts/build_backtest_dashboard.py
PYTHONPATH=. qlib_venv/bin/python scripts/check_dashboard_static_export.py
```

The refresh script discovers registry rows with `keep_actor=true`, non-dropped
status, a retained actor, and a resolvable `profile.yaml`. It writes
`dashboard_data/model_replay_freshness.json`, which the static checker reports
as `model_replays=<ready>/<total>@<safe_backtest_end>`. The checker also reports
`paper_latest_signal=<YYYY-MM-DD>` so dry-run/latest-signal freshness is visible
even when ordinary non-dry `paper_trading` rows have not advanced.

Qlib daily backtests need a following calendar boundary, so replay curves target
`safe_backtest_end` (usually the penultimate qlib calendar date). Paper trading
and latest signal artifacts may legitimately use `latest_data_date`, one bar
newer than the replay curve.

`production/soxl_daily_scheduler.py` runs the model replay refresh before
dashboard build by default. Use `--skip-model-replay-refresh` only for fast
diagnostic runs where stale model curves are acceptable.

When working in an isolated or partial worktree, verify the current qlib
calendar/test frame before treating `dashboard_data/model_replay_freshness.json`
as authoritative. If the freshness file reports dates beyond the visible qlib
data in the current checkout, use the penultimate visible qlib date as the
actual safe replay end and record the mismatch in the runtime card.

### Interactive Main Chart Reruns

For selectable-window reruns from the Main Chart, use the dashboard API server,
not a plain static server:

```bash
qlib_venv/bin/python scripts/dashboard_server.py --port 8765
# open http://127.0.0.1:8765/dashboard.html
```

The chart Start/End inputs control only the visible chart window. The Run Model
Backtest inputs use the replayable model window, so they are not locked to the
short `paper_trading` display range. For profiles listed in
`dashboard_data/model_replay_freshness.json`, the API should warm up from the
model replay CSV start and full `TEST_SEG`, then slice to the requested dates so
`position`, `strategy_nav`, and `action` align with the saved model replay CSV.
The response should expose `warmup_start_date` and `replay_aligned` for UI
diagnostics. A successful rerun is registered in the browser as
`rerun:<profile>:<start>:<end>` using the effective returned window and selected
in the Model dropdown. Rerun API rows should carry OHLC/indicator fields when
market data is available. The Main Chart must still draw a full `close || price`
SOXL line and a visible position line; OHLC candles are supplemental and must
not suppress the price line if enrichment is incomplete.
Opening `dashboard.html` through `file://` or a plain `python -m http.server`
can inspect static data. Backend model inference still needs
`scripts/dashboard_server.py` running at `127.0.0.1:8765`; the static page will
fall back to that API if its own origin returns `501`/`405`/`404` for
`/api/run-backtest`.

When debugging Main Chart freezes, check for repeated Plotly event registration
first. `renderChart()` is called by range, version, zoom, rerun, and segment
controls, so `plotly_hover`, `plotly_click`, and `plotly_doubleclick` handlers
must be bound once per chart DOM node and read fresh rows from node-owned state.
Do not close over per-render `rows` in repeatedly registered handlers; hover
lookups should use a date map instead of scanning the row array on every mouse
move.

For `web/dashboard-v2`, the equivalent freeze check is: `renderMarketChart()`,
`renderPositionChart()`, and `renderNavChart()` must remove the previous chart
for a container before creating a new one, and hover/crosshair callbacks must
only schedule inspector updates. Range buttons and keyboard shortcuts should
call `applyChartRangeCommand()` on existing chart handles.

Dashboard V2 currently has two inspection surfaces: root `dashboard_v2.html`
and the typed source under `web/dashboard-v2/`. Do not fix only one surface.
For feature-comparison work, verify both the root HTML contract test and the
`web/dashboard-v2` Vitest suite. The BUY/SELL feature table must compare
`feature_action_summary` across models, not only the selected model. Limit rows
per model (for example top 8 per model) before flattening; a global `slice()`
can hide every model after the first wide feature schema.

Version-selector rows from `dashboard_data/index.json` are only summaries. If
`DATA.versioned[version]` exists but lacks `detailed[ETF]`, the frontend must
still fetch `dashboard_data/versioned/<version>/<ETF>.json`; otherwise the Main
Chart silently falls back to the current ETF rows and shows a wrong window.
The converted `soxl_backtest_policy_reimplementation_v1` buy/sell path is a
`reference_baseline` dashboard version, not a runnable inference profile.

If the dashboard opens on an older run after fresh training, check:
- whether the latest `*_soxl_daily.csv` was written
- whether `scripts/build_backtest_dashboard.py` was rerun
- whether browser localStorage is pinning a manual old version
- whether `scripts/check_dashboard_static_export.py` reports
  `latest=paper_trading` when `paper_trading` is exported
- whether `dashboard_data/model_replay_freshness.json` reports stale, failed,
  or skipped model replay profiles

### Static Price And Paper Trade Correctness

Static `dashboard_data/versioned/<profile>/SOXL.json` payloads must retain
market fields needed for the price row: `open/high/low/close`, `volume`,
`ma180`, and dashboard indicators. Do not compact those fields away after
merging OHLC data.

For `paper_trading`, only use rows with non-dry per-date `summary.json`
metadata when such metadata exists. Old seed rows without a summary can make the
paper chart start from a stale price baseline. Rebase `buyhold_nav` to the first
displayed paper account value after filtering.

Do not synthesize a terminal `SELL` just because the final row has positive
position. Preserve explicit `HOLD` when no order was executed. Suppress
impossible actions such as `BUY` with zero position or `SELL` from a zero
position state.

The visible historical model-comparison table and Training Curve were removed
because their stale summary metadata was misleading for current static
inspection. Keep `dashboard_data/model_versions.json` only as a static export
integrity artifact unless a new reliable comparison design is added.

### Add a New Subplot
1. In `scripts/build_backtest_dashboard.py`, edit `_build_layout_all()`:
   - Increase `rows` in `make_subplots()`
   - Add a new `subplot_titles` entry
   - Update `row_heights` to allocate space
   - Add axis styling in the loop
2. In the JS `renderChart()` function, add a new trace block:
   - Extract data arrays from `rows`
   - Push a Plotly trace with correct `xaxis`/`yaxis` (e.g. `x5`, `y5`)
3. Regenerate and test.

### Add a Feature Column to Hover Tooltip
1. Add the column name to `FEATURE_COLS` in `build_backtest_dashboard.py`.
2. In the JS `updateInfoPanel()` function, add an info-row element:
   ```html
   <div class="info-row"><span class="info-k">NewFeature</span><span class="info-v" id="infoNewFeature">-</span></div>
   ```
3. In JS, populate it in `updateInfoPanel()`:
   ```js
   document.getElementById('infoNewFeature').textContent = f.new_feature != null ? fmtNum(f.new_feature, 2) : 'n/a';
   ```
4. Regenerate.

### Add a New ETF to Generalization
1. Ensure `runtime/generalization/detailed/{etf}_detailed_trades.csv` exists.
2. Ensure the ETF is listed in `runtime/generalization/detailed/summary.json`.
3. Regenerate dashboard — the ETF will appear in the select dropdown automatically.

## Legacy Architecture

| Layer | Technology | Responsibility |
|-------|-----------|----------------|
| Data | Python (pandas, csv, json, pickle) | Load backtest results, merge features, scan model versions |
| Layout | Plotly Python (`make_subplots`) | Generate 4-subplot layout JSON (NAV+Trades / Position / Excess Return / Drawdown) |
| Rendering | Plotly.js (CDN) | Browser-side interactive rendering, zoom, pan, hover, crosshair spikes |
| UI | Vanilla HTML5/CSS3/JS | Controls, metric cards, tables, info panel, state persistence |

## Legacy Features

### Mouse / Touch
- **滚轮缩放**: `scrollZoom: true` — 在图表区域滚动鼠标滚轮缩放
- **拖拽平移**: 按住拖拽平移（Plotly `dragmode: 'zoom'`）
- **框选放大**: 框选区域自动 zoom in

### Keyboard Shortcuts
| Key | Action |
|-----|--------|
| `+` / `=` | Zoom in (halve visible window) |
| `-` / `_` | Zoom out (double visible window) |
| `R` / `r` | Reset zoom |
| `←` | Pan left |
| `→` | Pan right |

### Crosshair + Info Panel
- **十字准线**: `showspikes=True, spikemode='across'` 跨全图显示
- **右侧固定信息面板**: 鼠标 hover 时显示当日价格、仓位、所有特征值
- **仓位分布**: 4 档水平条形图（0 / 低 0-0.3 / 中 0.3-0.7 / 高 0.7-1）
- **最近交易**: 显示最近 5 笔 BUY→SELL 配对

### Regime Shading
- VIX z-score > 2: 淡红色背景（高压力区）
- VIX z-score < -1: 淡青色背景（低波动区）
- 覆盖全部 4 个子图

### Trade Performance Table
- 点击表头排序
- 点击交易行 → zoom 到该交易日期 ±5 天
- 显示: 入场/出场日期、持仓天数、收益率、PnL、累计、Avg VIX、Avg RSI

### Trade Quality Stats (Kelly Formula)
- **凯利比例** (Kelly Ratio): `win_rate - (1-win_rate)/R`
- **期望收益** (Expectancy): `win_rate*avg_win + (1-win_rate)*avg_loss`
- **收益因子** (Profit Factor): `gross_profit / abs(gross_loss)`

## Troubleshooting

### Dashboard shows blank chart area
- Check browser console for Plotly.js load errors (CDN blocked?)
- Verify `PLOTLY_LAYOUTS` is present in generated HTML

### Features missing in hover
- Check `data/features_v2.pkl` exists and covers the date range
- Verify `_features` key is present in DATA rows (search generated HTML)

### File too large
- The generated HTML embeds all data inline. For >5 ETFs or very long histories, consider splitting into per-ETF pages or lazy-loading data.

### Version disappears after scheduled rebuild
- Check whether the source `runtime/model/card/<profile>/<profile>_soxl_daily.csv` was intentionally removed after a profile was dropped.
- Retained static evidence under `dashboard_data/versioned/<profile>/SOXL.json` should remain selectable even without the source CSV.
- `scripts/build_backtest_dashboard.py` loads retained dashboard exports as `retained_dashboard_export`; verify with:
  ```bash
  qlib_venv/bin/python -c "import json; d=json.load(open('dashboard_data/index.json')); print(d['version_summaries']['<profile>']['meta']['source_kind'])"
  ```
- Regression coverage belongs in `tests/test_dashboard.py` so scheduled paper/Vercel rebuilds cannot silently remove retained evidence from the index.

### Model version stays stale after refresh
- Check `dashboard_data/model_replay_freshness.json` for the profile's
  `result`, `before_end`, `after_end`, and `reason`.
- Confirm the registry row has `keep_actor=true`, is not `status=dropped`, and
  has both `runtime/model/card/<profile>/soxl_<profile>_actor.pt` and a
  resolvable `profile.yaml`.
- If two CSVs produce the same dashboard tag, the builder should prefer the
  matching profile directory. Regression coverage:
  `tests/test_dashboard.py::test_load_versions_prefers_matching_profile_directory_for_duplicate_tag`.
